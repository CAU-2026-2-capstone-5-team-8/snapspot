## 스크린샷 개인정보: 폰에서 먼저 읽고, 가린 뒤에만 보내요

중간발표 피드백에서 "스크린샷이 그대로 Gemini로 간다"(개인정보)와 "Gemini만 쓴다"(설계)는 지적이 함께 나왔어요.
그래서 스크린샷을 Gemini에 보내기 전에 **폰 안에서 먼저 읽고, 개인정보를 가리고, 꼭 필요한 만큼만 보내는** 단계를 넣었어요.

### 흐름

```
스크린샷 (앱 저장소에 1024px로 복사, 원본은 폰에만)
  → ① 폰 안에서 읽기 (ML Kit, 인터넷 없이)
       글자(한국어) · 바코드 · 얼굴의 위치
  → ② 개인정보 찾기 (core/Redact.kt)
       전화번호 · 이메일 · 주민등록번호 · 카드번호 · 10자리 이상 숫자(바코드 번호, 핀, 주문번호)
       + 바코드 · 얼굴
  → ③ 어디서 읽을지 정하기 (core/LocalRead.kt)
       LOCAL  기프티콘 규칙으로 브랜드 · 상품 · 유효기간을 모두 읽으면 여기서 끝 → 아무것도 보내지 않음
       TEXT   글자가 충분하면 가린 글자만 Gemini로 (예: "문의 [전화번호]")
       IMAGE  글자가 거의 없으면(포스터 사진 등) 개인정보 영역을 검게 칠한 이미지를 Gemini로
              TEXT로 읽었는데 이름·브랜드가 비면 IMAGE로 한 번 더
  → ①이 실패하면 아무것도 보내지 않아요 (가리지 못한 채 보내지 않음)
```

- 코드: 판단 규칙 `core/Redact.kt` · `core/LocalRead.kt`, 폰 안 읽기와 칠하기 `image/ShotReader.kt`, 글자만 보내기 `net/GeminiClient.kt`의 `extractText`
- `Screenshots.prepare`는 더 이상 이미지를 base64로 만들지 않아요. 밖으로 나가는 건 `ShotReader`가 정한 것뿐이에요.
- 가린 개수와 읽은 경로는 로그(`screenshot read: route=… masked=…`)로 남겨요. 아래 측정에 써요.

### 무엇을 가리나

| 종류 | 예 | 방법 |
|---|---|---|
| 전화번호 | 010-1234-5678, 02-123-4567, 070-… | 정규식 |
| 이메일 | me@cau.ac.kr | 정규식 |
| 주민등록번호 | 030301-3123456 | 정규식 |
| 카드번호 | 1234-5678-9012-3456 | 정규식 |
| 긴 숫자 | 바코드 번호, 핀, 주문번호 (10자리 이상) | 정규식 |
| 바코드 | 기프티콘 바코드 | ML Kit 바코드 인식 |
| 얼굴 | 게시물 속 사람 | ML Kit 얼굴 인식 |

날짜(2026.12.31), 가격(4,700원), 주소의 번지(여의대로 108)는 가리지 않아요. 장소를 찾는 데 필요해서예요.

### 측정 계획

실제 스크린샷 50~100장에 개인정보 위치를 사람이 표시해 두고 아래를 재요.

| 지표 | 의미 |
|---|---|
| 개인정보 가림률 | 표시한 개인정보 중 가린 비율 (놓치면 안 되는 쪽) |
| 잘못 가림 | 가렸는데 개인정보가 아니던 비율 (장소 이름·주소를 가리면 정확도가 떨어져요) |
| 경로 비율 | LOCAL · TEXT · IMAGE로 읽은 비율. LOCAL·TEXT가 많을수록 덜 보내요 |
| 정확도 유지 | 가린 뒤에도 장소 이름 · 브랜드 · 유효기간을 맞힌 비율 (이미지를 그대로 보낼 때와 비교) |
| 비용 · 시간 | 스크린샷 1장당 Gemini 호출 수와 처리 시간 |

### 한계

- 정규식에 없는 개인정보(이름, 아이디, 손글씨 메모)는 못 가려요. 인스타그램 아이디는 가게 계정일 수도 있어서 일부러 두었어요.
- 글자 인식이 틀리면(작은 글씨, 기울어진 글씨) 개인정보를 놓칠 수 있어요. 가림률 측정으로 확인해요.
- 기프티콘 규칙은 `KNOWN_BRANDS`에 있는 브랜드만 알아봐요. 없는 브랜드는 TEXT로 Gemini가 읽어요.
